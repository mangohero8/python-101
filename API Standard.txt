OAS: Does the OAS filename match the naming convention for the API type?
The link to the OAS should work if the Deployment Summary is filled out correctly.

For Base APIs:

The ApplicationName, Collection, VendorName are mixed case so as to be human-friendly.  The SupportingTeamInitials in many cases should be the ApplicationName's (SoR's) abbreviation but may represent a team that supports many Applications.

Huntington API: API's that follow the Data Architecture Domain Models
 "HNB_<Collection>_<Version> <CCYYMMDD>-<SupportingTeamInitials>.yaml"

Orchestration/Composite API: APIs that span multiple domains (Ex. spans Customer and Account domain) and follows ALL other HNB standards and Data Architecture Domain Models.  This typically DOES NOT have its own data store and instead is orchestrating across other domains that DO have a data store
 "Orch_<Collection>_<Version> <CCYYMMDD>-<SupportingTeamInitials>.yaml"

Application specific: API’s that follow HNB API standards but DO NOT follow the Data Architecture Domain Models and will only be consumed internally by the Application

"App_<ApplicationName>-<Collection>_<Version> <CCYYMMDD>-<SupportingTeamInitials>.yaml"

Vendor: APIs that define a vendors API
"<VendorName>_<Collection>_<Version> <CCYYMMDD>-<SupportingTeamInitials>.yaml"

Application Support Module (i.e. Fuse UI interface):  Application Specific Support Modules which follow NEITHER the Huntington modeling NOR the API conventions. Most legacy UI specific Fuse modules that were built prior to the API Standards fit in here, and these should be converted to an ‘App’ API.  No new APIs should be created as AppSM.
"AppSM_<ApplicationName>-<Collection>_<Version> <CCYYMMDD>-<SupportingTeamInitials>.yaml"

For EEH Event Variants:

The pattern is: "App_EEH-Events-<Collection>_<Version> <CCYYMMDD>-<SupportingTeamInitials>.yaml"

Note:  The "ApplicationName" should be the name - or alias or abbreviation - as registered in the CMDB.  For example, the "Mobile Smartphone Application" has an alias of "Mobile" so the ApplicationName should be "Mobile".  Similarly, the "Enterprise Event Hub" has an abbreviation of "EEH" so that is used for its APIs.  The API Governance Team can help deconflict any overlaps which may result in a modification to the CMDB.

Note:  The Supporting Team must be an IT Team and not a business or operations team.  See the FAQ - "What do the Owning Team Initials on the API Deployment Summary represent?" or the API Governance for a list of initials.

OAS: Does a Mainframe implementation OAS/Swagger support the Mainframe zCEE needs?
If an Application is on the Mainframe and it needs to call an API off-host (for example, call the EEH-Events API to send an Event to the EEH), an additional YAML file is required that is based on the base API AND its EEH Variant.

The tool used by z/OS Connect Enterprise Edition (zCEE) requires a Swagger 2.0 file in JSON to define the utilities, configurations, and copybooks necessary for a mainframe program to call out through zCEE to the AGW.  The Heartbeats example (which ends in Swagger.yaml) illustrates the difference between the EEH Variant of Heartbeats (App_EEH-Events-Heartbeats_2.0) and the mainframe required Swagger 2.0.  This file can then be converted to JSON (using the Swagger Editor) and fed into the zCEE tool.

Note that the Swagger used by the zCEE tool requires additional information that may not be in the distributed version of the API because the mainframe copybooks require fixed-length strings and arrays.  Therefore:

For every array in the Swagger make sure each array has a "maxItems" value on the array schema definition.
Similarly, for any string element make sure there is a "maxLength" value or the converter will default to 256 characters which may result in an abnormally large copybook.
Note that any field that is a real (float) number on the mainframe may not convert through zCEE into a number in JSON correctly (for example, a value of "25.32" might come across as "25.3199999999".  Thus, in the Swagger ensure that all fields are strings.
More details on zCEE, its peculiarities, and remediation can be found here: AGW zCEE User Guide​​​​​​​

OAS: Is the OAS info version correct and consistent with the YAML filename?
The current OAS "openapi" stanza refers to the version of OAS - "3.0.3" as of writing.

The version in the info stanza is a 3 part (major,minor,patch) version number of the API being defined.  The first 2 parts (major,minor) will be used in the version number within a URL (i.e. in the Fuse module) and are distinct identifiers for the content of the API.  The third part (patch) is only used in the info stanza of the OAS.

The version should only be updated when necessary, not with each change.  The gudeline on when to increment a version of a HNB or APP API is:

<patch> is incremented in the info stanza of the OAS with any change made to an API that has already been approved

<minor> is incremented with new functionality and significant backward-compatible changes

<major>is incremented on any non-backward compatible modifications or significant processing changes

No more than 3 major versions should be exposed at the Production API Gateway at any time (ie. current, previous, sunset, deprecated).

If this is a Vendor API, it should match the number as published by the Vendor.  Note that in the URL version, the version will be 2 parts (major,minor).

For example:  The "Heartbeats_2.0" API may have a info version of "2.0.1" but will use "2.0" in the YAML filename as well as the module URL...  https://api.huntington.com/hnb-hrtbt/2.0/heartbeats

OAS: Are the scopes set correctly at the top and with each operation?

OAS: Does the Collection schema follow the same hierarchy as the example?
The pattern of definition of a base and most of the other hierarchies in the OAS model must be followed consistently to leverage the automation and onboarding tools that are currently in development.

In general, each operation's 200 response should include a $ref for the HTTP_200 scheme in scope (HTTP_200, HTTP_200_summary, HTTP_200_collection, or HTTP_200_collection_summary).  In some cases (especially a GET against a specific resource), the HTTP_200_EXPANDEDRESOURCE will be useful.

The HTTP_200* schema will point to the Response, Response_collection, Response_summary, Response_collection_summary as appropriate.

This Response* schema will include Response-specific structures and point to the base or base_summary schema.

The base* schema will then point to the appropriate definition which is either _RESOURCE, _SUMMARY, or _EXPANDEDRESOURCE.

Schemas below the *_RESOURCE are generally API specific and structured according to API modeling best practices.

Using the same hierarchy and schemas from the Heartbeats example ensures the standard aggregates '_metadata' and 'payload" are present in the Request(s) and Response(s).  Likewise, the statuses array will be present and referenced correctly.

OAS: Do fields defined as number and integer data types use the correct validation keywords?
Any field defined as a number or integer data type should only use validation keywords of:

minimum - The smallest number that can be passed must be greater than or equal to this number
maximum - The largest number that can be passed must be less than or equal to this number
exclusiveMinimum - The smallest number that can be passed must be greater than this number
exclusiveMaximum - The largest number that can be passed must be less than this number
multipleOf - Identifies the numbers passed must follow this cadence.  For example, if you have a field called nickelBalanceAmount and are adding the total balance for all of nickels, it may have a multipleOf set to .05 so the balance is always in 5 cent increments.
NOTE that minLength and maxLength are not valid validation keywords for number or integer data types.

OAS: Do fields defined as string that include an enum have minLength and/or maxLength validation keywords?
Any field defined as a string that has an enum SHOULD NOT have the minLength or maxLength validation keyword.

OAS: Does the operationId follow the naming convention?
The naming convention of the operationId is: <Method><Collection Name><Limiter><Set>

Method
The HTTP method being executed (GET/POST/PATCH/PUT/DELETE)
If it is a POST /retrieve, it should start with retrieve instead of post
If it is a POST/delete supporting a set of resources being deleted, it should be delete instead of post
Collection Name
Should be plural for GET's against the Collection (resource id IS NOT a path parameter)
Should be singular for GETs against a specific resource (resource id IS a path parameter)
For the /ping methods, both will have the collection name in the operationId
Limiter
If the path has a limiter, it should be included
Ex. /summary
For Ping
<collection>/ping should have Ping as the last portion of the operation id
/ping should have PingProxy as the last portion of the operation id
Set
If you are exposing methods that allow actions to be taken on a 'Set' or multiple instances of the collection (they should be within the 'Set' tag), the operation Id should end in Set

Modeling: Do the Collection name and abbreviations match the naming standards?
Applies to: HNB, App Classification APIs

The Enterprise Information Model lays out the guiding naming and relationships between the Collections.  This model is evolving and will be filled out as use cases require.   See API Standards.

Each node is separated by a dash '-'

Only the first character of a node should be upper case, all others should be lower case

 

Collection names are defined (almost always) as plural nouns.  Some collection names have multiple tokens which results in a combination of singular and plural to these general guidelines:

Right most token is plural

Second-level is plural

First level is singular if more than one level and plural if only one level

In addition to a name used in the API definition (like "customer-relationships-accounts") there are abbreviations that can be used for each of the tokens and the full name (like "cu-rel-acnt").  These abbreviations are assigned by API Governance.  The abbreviation - or a variation ("cu-rel-acnt" vs. "cuRelAcnt") can be used in the module names within APIs or in the naming of the deployable artifacts to maintain a consistent naming convention across the enterprise.

Within a standard API, the module name should use the abbreviation rather than the full collection name.  Vendor APIs differ from this norm considerably.

Modeling: Are the paths marked with the proper tag?
The plural stylized <Collection Name> (for example "Customer Relationships Accounts") is for the POST and the collection GET operations as these operate on the collection (a POST is a request to "create a new resource within the collection" and the GET is essentially a search).

The singular version ("Customer Relationships Account") should be used for GET of a specific Resource as well as DELETE, PATCH, and PUT as these all operate on a single resource.

Of of 2023-05-22, a new "<Collection Name> (set)" tag has been introduced for PUT, PATCH, and DELETE operations that work on multiple individual resources.  For example, "POST /heartbeats/delete" is tagged as "Heartbeats (set)" as it is a singular operation on multiple resources.  Note this syntax is an alternative to the "DELETE /heartbeats/resource1,resource2,resource3" which would attempt to delete 3 resources.

Modeling: Are the field names consistent with types and reserved words/suffixes?
Here is a list of reserved words and/or suffixes for all fields and aggregates:

The suffix "Id" is reserved for unique identifiers for collections in the Enterprise Information Model and/or approved by API Governance.
A suffix of "id", "Identifier", "identifier" should not be used for any fields or aggregates.
The suffix "Reference" can be used to identify an instance outside of a Huntington collection.
The suffix "Timestamp" represents a timestamp and must meet the ISO 8601 standard for time specification.
The suffix "Date" represents a single day and must meet the ISO 8601 standard for date specification.
The suffix "Period" represents a time range and must meet the ISO 8601 standard for period specification.
The suffix "Indicator" represents a Boolean (in OAS "boolean") and may only contain the values of true or false
Not 1/0, T/F, Y/N, True/False, etc.
It should NOT be quoted (i.e. "true" or "false" are NOT equivalent to true or false)
The suffix "Code" is reserved for programmatic identifiers and should be matched with a corresponding "Description" field.
The suffix "Description" is reserved for human-friendly descriptions of the corresponding Code field and should be included in all RESOURCE and SUMMARY definitions.
The suffix "Amount" is used for any field of a monetary value.  It should be used in conjunction with a currencyCode.
Note that a float (in OAS number) is the conventional type for this field but some tooling will not honor the precision specified in the OAS so a string representation in the JSON should be used.
The field "currencyCode" is reserved for the ISO 4217 currency code as a 3-character UPPERCASE string.  No corresponding currencyDescription is required.
Certain words should not be used as standalone field or aggregate names:
status (or statuses)
number
distance
amount

Modeling: Is accountId used in lieu of accountNumber?
To reduce the exposure of PII data (in this case account number) it is preferred that only the Accounts collection owned by CMDS expose the account number.  Any other collection that needs to reference the account should only include the account identifier and not account number.  Any system that has the account identifier and has a legitimate use case for needing the account number would call the Accounts API to retrieve the account number for that account identifier.

Since the CMDS Accounts collection is used as one place to see summary information for ALL account types and only owns the account identifier and is a 'system of reference' for account number, product type, and product sub type (meaning the detail account objects is the owner of the account number, product type, and product sub type and it is included in the Accounts object for reference only) it is allowable for account number to be included in ONLY the detail account collection for that product type.  Account number CANNOT be included in other APIs within that domain.

Modeling: Are the element (field) names and aggregates consistent across related APIs?
This is more of a modeling check to ensure new names for common fields aren't accidentally introduced into the overall enterprise model.


Modeling: Are all Timestamp fields 32 characters long per ISO 8601?
Strings are not REQUIRED to have a length but all Timestamps MUST BE ISO 8601 consistent.  Example pattern: "CCYY-MM-DDTHH:MM:SS.mmmmmm+05:00" or "CCYY-MM-DDTHH:MM:ss.mmmmmmZ".


Modeling: ​​​​​​​Are all Date fields 10 characters long per ISO 8601?
Strings are not REQUIRED to have a length but all Dates must be ISO 8601 consistent.  Example pattern: "CCYY-MM-DD".


Modeling: Are all Booleans or other binary fields suffixed with "Indicator" and represented as true/false?
Fields that contain Yes/No, 1/0, T/F should be redefined as Booleans and mapped to true or false (not ‘true’ or ‘false’).  This is a JSON standard. A default value should also be defined.


Modeling: Do all fields with a name ending in "Code" have a corresponding "Description"?
A "Code" field is intended for use by an application while a "Description" field is intended for human consumption.  An application that exposes codes should also provide a translation in the description.

Note:  The "currencyCode" (example: "USD") generally has a "currencyDescription" as defined by the ISO 4217 standard (example: "United Stated Dollar").  However, because currencyCode is so prevalent and is a universal code, the "currencyDescription" can be dropped in APIs that are not intended to be UI facing.  There is a separate API to translate currencyCode to currencyDescription (DOCUMENTATION TBD).


Modeling: Are all fields with a name ending in "Type" descriptive enough to stand alone and are they enumerated in the field documentation?
A "Type" field is normally used by a program to identify specific variants of an object and is intended for processing by a program and not relevant to a human although exceptions do exist so it is most helpful if the Type is at least stylized to be human friendly.

For example, transactionAmountType has enumerated values of "credit" and "debit" instead of C/D or some other shorthand (which would require a Code/Description combo).

ReST: ​​​​​​​Is the correlationId properly present in any POST, PATCH, or PUT operation?
This is part of the normal _metadata structures so as long as the schema hierarchy is followed and the __common_metadata_* inclusions exist, this will be covered.

ReST: Do references to other official collections use the proper structures and identifiers?
If an API references another collection's _RESOURCE (like "customer-relationships-accounts_RESOURCE") then the reference must have the same name and use a subset of the structure defined in the _RESOURCE.  Under current methods, all of the referenced schemas from the referenced API must be copied into this API (place them at the bottom).

Do not try to reorganize another API's content or make definitions to override the SoR's definition.  Use the same names and remove fields you don't need in your inclusion.

If an API is only referencing the unique identifier, then only it needs to be copied into the API, not the entire _RESOURCE.  Note that the EQH query parameter "expand_resources" allows the EQH to fetch the referenced entity, based on the unique identifier, and include it within the returned payload.


ReST: Are the primary identifiers for a resource a GUID?
In all cases, the unique identifier for a resource should be an opaque string that the caller should not process.  These should NOT be represented as numbers in OAS but as "string".

In nearly all cases, the unique identifier should be a GUID so as to ensure opaqueness AND provide a security defense against an attack vector of a small namespace.

THIS IS ESPECIALLY TRUE OF INTERNET FACING APIs THAT PROVIDE CUSTOMER AND ACCOUNT DATA (like the customerId and accountId).  Although these two principal APIs have not yet been addressed (as of December 2022), the decision HAS been made that these APIs cannot be exposed to Fintechs, Akoya, and the Mobile Smartphone Application and the ROL Browser Application until this is addressed.

ReST: Is the resource ID the only field that is used as a path parameter?
Only the resource id of the collection can be used as a path parameter in any of the operations within the OAS.  All other fields needed to filter the result set should be query parameters.

Example:

For collection customer-relationships-accounts, the resource id is customerRelationshipsAccountId, and only that field can be used as a path parameter in an operation
Correct: 
GET /customer-relationships-accounts/{customerRelationshipsAccountId}         <- resource id is a path parameter
GET /customer-relationships-accounts?customerId=12345                                 <- customerId is a query parameter
GET /customer-relationships-accounts?accountId=98765                                   <- accountId is a query parameter
Incorrect
GET /customer-relationships-accounts/{customerId}                                           <- customerId is a path parameter
GET /customer-relationships-accounts/{accountId}                                             <- accountId is a path parameter

ReST: Are all request payloads/query parameters a subset of the collection as defined in the _RESOURCE?
The <collection>_RESOURCE object defines the attributes that are exposed within that collection, and only those fields are able to be acted upon by methods the OAS.  This means that All method request objects or query parameters within the OAS need to be a subset of this definition.
